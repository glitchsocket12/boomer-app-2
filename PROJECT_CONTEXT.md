## 1. What Grove is

**The frame:** *Your life is bigger than your memory. This is where the rest of it lives.* Grove is an asset you build — a private record of your people that compounds every year — and it stays honest that forgetting is the real problem, framed as **foresight, not diagnosis**: build it now, and if things ever do start to slip, you're covered. ("In Fight of Forgetfulness" survives in that reading, further down the landing page — never as the hero.)

**The long tail IS the product** (founder, 2026-08-22 — the correction that drove this repositioning): Dunbar's 150 is the ceiling on relationships you actively *maintain*; it was never the size of a social life. The founder's account holds 724 people, and the ~574 beyond the close tier are the point — the minor characters and passers-by who give a social world its **texture**. They are exactly who a brain drops first and exactly who nothing else stores. Never treat the long tail as import noise to be filtered away; the demo's ~180-person generated roster exists to argue this.

**Who it's for:** people carrying more relationships than anyone can hold in their head — defined by the **volume and duration** of a life, not by age. Big extended families, a few moves, a long career, in-laws, kids' friends' parents, teams. Age-neutral by construction, since the stated cause is volume rather than decline. Supersedes the vaguer "extrovert who wants to show up better" framing and keeps the 2026-07-19 de-age-gating.

**What makes it more than a CRM: Notebooks** (founder, 2026-08-22 — *"notebooks are the key to this… it's notes for your daughter to give her on her 18th birthday; a place to file away feelings about work"*). Every competitor is either a personal CRM (60+ of them: Dex, Clay, Cloze, Folk, Monica) or a memory-book/prompt product (Keepsake, FamilySearch Memories, Memoriz). None hold the long tail, the graph, the events **and** a private internal record together. Don't let copy or features drift into personal-CRM language — it's crowded and it makes the app feel like work.

| It is | It isn't |
|---|---|
| A private record you own and keep | A public feed, a profile, an audience of strangers |
| People + events + groups, connected | A contact list, a calendar, a photo dump |
| The long tail as much as the inner circle | A tool for maintaining your top 150 |
| Also a record of your own inner life | A diary or a journal (never print either word) |
| Better the longer you use it | Something you open in a crisis |
| Honest that memory is finite | A diagnosis, a medical product, an age bracket |

The founder is non-technical, building hands-on; the product's value is the quality/warmth of what it gives back, not what it stores.

**External vs internal** (founder framing, 2026-08-18, adopted as the organising idea for §7 Notebooks): Events are the app's EXTERNAL record — what happened, who was there. Notebooks are the INTERNAL one — what you thought, what you liked, how you were doing. Before Notebooks the app had only the external half; a `notes` row was required by CHECK constraint to hang off a person, group, or event, so a movie you loved or how a Tuesday felt had nowhere to live. Corollary the product follows: the app supplies NO categories or labels for the internal side — the user titles their own notebook, which is how the product avoids ever printing "diary" or "journal" (founder: either word reads as gendered and would put some users off before they'd written anything).

## 2. Stack & Infrastructure

- **Frontend:** React via Vite, TypeScript (accidental — StackBlitz default; keep types light, not strict).
- **Backend:** Supabase (Postgres + auth + Deno Edge Functions). All AI calls happen in Edge Functions only — API keys never reach the browser.
- **AI:** Anthropic Claude API, model `claude-sonnet-5` in all functions (an invalid model string fails silently — see guard §12).
- **Speech-to-text:** OpenAI `gpt-transcribe` (streaming) via the `transcribe` function; needs `OPENAI_API_KEY` in Supabase secrets (project-wide list under Edge Functions → Secrets). $0.0045/min, ~half whisper-1's error rate. Was `whisper-1` until 2026-08-18. Sends the roster as `keywords[]` so names spell correctly. Owns the authoritative transcript because the free Web Speech API is unreliable in iPhone Safari (it exists there since iOS 14.5, contrary to what this doc said until 2026-08-18 — it just fires `onresult` once and dies), and the founder's end goal is an iPhone app.
- **Hosting:** Vercel, live at `https://boomer-app-2-eight.vercel.app/`, auto-deploys on every push to `main` (repo: `github.com/glitchsocket12/boomer-app-2`). `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` set in Vercel project settings; Vite bakes them in at build time. Vercel CLI (`npx vercel`) installed as a fallback deploy path.
- **Address autocomplete:** Geoapify (geoapify.com — verified free tier, 3,000 req/day, no credit card; Radar was tried first but turned out enterprise/quote-only despite its docs), key in `VITE_GEOAPIFY_API_KEY` (local `.env` + Vercel project settings) — client-side calls only, no Edge Function proxy. Key created and working in local dev; still missing from Vercel's production env vars — see §10.
- **Event enrichment APIs (2026-08-17, item 21):** two keyless free APIs called only from `enrich-event` — **ESPN** (`site.api.espn.com/apis/site/v2/sports/{sport}/{league}/…`) for game results, and **Open-Meteo** (`archive-api` for historical weather + `geocoding-api` for place→lat/lon). No secrets, no Anthropic tokens. Two caveats: ESPN publishes **no official public API** (undocumented, unsupported, could break without notice — every call is confined to `_shared/eventEnrichment.ts` so a provider swap is one file), and Open-Meteo's free tier is **non-commercial only** under CC-BY (fine today; if Grove ever charges, buy their plan or swap the source — same one file, and the "Weather data by Open-Meteo" credit in the box satisfies the licence).
- **Dev:** local folder, this repo. `npm run dev` (port 5173; respects `PORT` for the browser-preview tool), `npm run build`, `npm run test` (Vitest — `src/lib/` pure helpers plus 16 `_shared` Edge Function modules; each function's own `index.ts` orchestration is deliberately uncovered, since `serve()` + a live `fetch` have no seam to inject). `npm run lint` (oxlint), `npm run check:functions` (`deno check` on every function's `index.ts`), `npm run check` runs all four.
- **Deploying Edge Functions:** `npx supabase functions deploy <name>` using `SUPABASE_ACCESS_TOKEN` (persisted in local `.env`, gitignored, since 2026-08-03 — no longer pasted per-session), or paste the file into the Supabase dashboard and click Deploy as fallback. `supabase/functions/_shared/` is bundled automatically.
- **Schema changes:** applied directly via the Management API (`POST /v1/projects/{ref}/database/query`, same persisted token) as the default path now; SQL saved under `supabase/migrations_manual/` and handed to the founder to paste in the SQL Editor only when a write gets blocked or is a large/production-risk bulk change.
- **Google Photos import (2026-07-30, item 27):** this app's first OAuth flow and first Supabase Storage usage — see §3 `lib/googlePhotosAuth.ts`/`lib/googlePhotosImport.ts`/`PhotoImportReview.tsx`, §6 `photo_connections`/`photo_clusters`/`photos`, §10 for what's still needed before it's live. New Edge Function secrets `GOOGLE_PHOTOS_CLIENT_ID`/`GOOGLE_PHOTOS_CLIENT_SECRET` (server-side only, from a Google Cloud OAuth Client) and a new Vercel env var `VITE_GOOGLE_PHOTOS_CLIENT_ID` (the client ID itself isn't secret). A private `photos` Storage bucket holds resized (~1600px) copies, RLS-scoped per user by folder prefix — deliberate choice over leaving photos live in Google, since a picker session's access to a picked item expires with the session (no stable long-term pointer available).
- **Sign in with Google (2026-08-03):** `Login.tsx` has a "Continue with Google" button using Supabase Auth's built-in OAuth (`supabase.auth.signInWithOAuth`) — unlike the Google Photos flow above, this is fully handled by Supabase (no custom Edge Function/callback route). Not usable yet — see §10 for the two founder steps left.
- **The 1000-row cap (Edge Functions swept 2026-08-10, browser swept 2026-08-11 — item 88):** PostgREST caps ANY response at 1000 rows and reports nothing — no error, no flag, just a shorter array, so an unpaged account-wide read looks successful while quietly omitting data. The fix is `fetchAllRows()`, which pages and REQUIRES an `.order()` (paging without a stable sort duplicates and skips rows, which is worse than the truncation); it exists twice, `_shared/pagedSelect.ts` for Deno and `lib/pagedSelect.ts` for the browser, and `lib/pagedSelect.test.ts` covers the seam and the exact-multiple-of-1000 boundary. **Both sides are now swept** — 58 browser sites across 26 files. Tables already over the cap on the founder's account: `contact_import_candidates` 2008, `notes` 1502, `person_groups` 1183. `people` sits at 724 and is the next to cross. Reads bounded by ONE record's fan-out (a person's own notes, an event's own sub-events) are deliberately left unpaged — they scale with that record, not the account. **Embedded selects are NOT capped** — verified empirically (all 796 event-attached notes come back through `moments.select("notes(...)")`), so single-parent embeds like update-group's roster are fine. Writes are unaffected. Narrowed reads (`.eq()` on one id, `.limit(n)`) are fine. When adding any new account-wide read, page it. **The first sweep covered Edge Functions only; the browser reads the same tables directly and was swept 2026-08-10 (second pass) via `src/lib/pagedSelect.ts`** (browser twin of the Deno helper — keep the two in sync). That pass fixed a live bug: Home's "Connections to make" card read `person_groups` unpaged, so 183 of 1183 memberships were invisible and read as "not a member yet" — 21 of its 29 questions were about people already in the group, which is why an accepted suggestion came back on the next visit. Paged now: `suggestConnections.ts`, `suggestEventGroups.ts`, `dismissedSuggestions.ts`, `familyTree.ts` (loadFamilyGraph), `relationshipsTable.ts` (whole-table branch). **Still unpaged: the page-level reads in `People.tsx`, `Groups.tsx`, `Circle.tsx`, `Events.tsx`, `FamilyTree.tsx` etc. — see backlog item 88.**
- **Bundle / code splitting (2026-08-17):** every page is `lazy()`-loaded in `App.tsx` and built as its own chunk. Entry bundle 466kB (133kB gzipped), down from one 1,123kB (303kB) file holding all 41 screens. `Landing`/`Login` stay STATIC — they're the logged-out first paint, so lazy-loading them would add a round trip to the moment being optimized; `Home` is lazy but prefetched on mount so it overlaps the auth round trip. Anything App.tsx needs at module scope must NOT be imported from a lazy page (that drags the page back into the entry chunk) — this is why `lib/eventFilters.ts` exists, split out of `pages/Events.tsx`. `Suspense` fallbacks sit INSIDE `ErrorBoundary` so a chunk that fails to download surfaces as an error instead of a spinner that never resolves.
- **Token-free live verification (no login needed):** a column exists if PostgREST returns 200 (400 if not, via anon key); a function is deployed if its URL returns its own error/401 rather than Supabase's `NOT_FOUND`.

## 3. Frontend map

_One line per file: path — what it does. No dates, no history (§11 budget). **Detailed per-file rationale is archived in PROJECT_HISTORY.md — search it by filename when you need the "why" behind a specific file.**_

**Shape:** no CSS framework — everything is inline `style={{}}` reading tokens from `lib/theme.ts`. Every page is `lazy()`-loaded in `App.tsx` (§2). Ten pages (Home, People, PersonDetail, Groups, GroupDetail, Events, EventDetail, FamilyTree, Notebooks, NotebookDetail) split into a data-fetching container plus a pure exported `*View`; `src/pages/demo/` feeds `lib/demoData.ts` into those same `*View`s, so a UX edit updates the public demo automatically. ## 5. AI cost & caching architecture (see CLAUDE.md rule 3 — non-negotiable)

- **DB-cached outputs** (generate once, serve from a column, refresh on data change or manual button): `people.key_facts`, `groups.summary`, `moments.summary`, `home_suggestions`. Never re-call the API for unchanged content.
- **Prompt caching, tiered by volatility (restructured 2026-07-20):** `converse`/`update-moment`/`update-group` each split their system prompt into ordered tiers, stable-to-volatile, each its own `cache_control` breakpoint: fully-static instructions (zero interpolated data) → a roster tier (people/groups/other-items — changes rarely, 1-hour TTL) → a hot-write tier (moments for `converse`; this-item's-own-state for `update-moment`/`update-group` — default 5-minute TTL) → today's date last, uncached (previously sat at the FRONT of one combined block and busted the whole thing daily). `add-fact`/`person-facts` also cache-marked. `summarize-group` deliberately has NO markers (under the ~1024-token minimum — nothing to gain). `summarize-moment` crossed that minimum with the 2026-08-10 sub-event instructions and now carries one breakpoint on its whole (fully static) system prompt — 1,268 tokens then, ~2,390 after the 2026-08-17 bullet rewrite, `cache_creation` on the first call and `cache_read` on the second, measured live (the whole-account sweep ran at `cache_creation: 0` after its first call). Nothing per-request may ever be interpolated into that string.
- **Every roster/moment query in these functions has an explicit `.order()`** — Postgres row order is otherwise nondeterministic and silently busts the cache-prefix match. Removing one kills caching with no error.
- Verify with `usage.cache_read_input_tokens` in responses when touching this code (confirmed nonzero live 2026-07-19; the 2026-07-20 redeploy is confirmed live via §10's 401 check — re-verify the usage field itself next time real chat traffic hits it).
- **The cache is scoped to the Anthropic ORG + WORKSPACE, not to the API key** (confirmed against Anthropic's docs 2026-08-12, during the key rotation). Rotating or replacing `ANTHROPIC_API_KEY` does not invalidate anything — do not tell the founder a new key starts cold. A `cache_read_input_tokens: 0` right after a rotation is explained by the outage itself (entries expire after their 5-minute/1-hour TTL), not by the key. The one real trap: a key issued in a DIFFERENT workspace gets a separate cache pool, which shows up as `cache_read` stuck at zero on *every* call, not just the first.
- **Conversation thread also cached (2026-07-20):** `_shared/promptCache.ts`'s `withMessageCacheBreakpoint` adds a `cache_control` marker to the last message in `messages` — the 4th and final breakpoint in each function (max 4/request) — so the growing back-and-forth itself gets cached too, not just the archive/roster tiers above. Previously the system-prompt tiers could hit cache while the whole message thread still re-paid full price every turn.
- **Relationship-extraction fanout, reduced 2026-07-20 (not eliminated):** `_shared/relationships.ts`'s `getRelationNames` now memoizes each person's parent/sibling extraction within one request (previously re-derived the SUBJECT's own list from scratch on every sibling compared against it) and checks `people.key_facts` before ever making a fresh Claude call, falling back to a live call only when Key Facts are empty/missing for that person. Cuts the ~12-call worst case when many siblings/parents are named at once; doesn't remove the ceiling. See PROJECT_HISTORY §14.

## 6. Database (Supabase / Postgres, RLS on everything, scoped to auth.uid())

_Every table and column is listed. Parentheticals state only LIVE constraints; migration histories and the reasoning behind each shape are archived in PROJECT_HISTORY.md — search it by table or column name. SQL lives in `supabase/migrations_manual/`._

### People and relationships

- **people** — `id`, `user_id`, `name` (first), `last_name?`, `nicknames?` (comma-separated "goes by" list, additive, chat-only, never displayed), `middle_name?`, `goes_by_kind?` (`first`/`middle`/`last`/`other`, null = `first`), `goes_by_other?` (only set when `goes_by_kind = 'other'`), `former_last_names?` (comma-separated, additive — maiden/former SURNAMES; folds into the SURNAME side of matching, never givens — §12), `gender?` (CHECK: `male`/`female`/`non-binary`/`other`; read in its own isolated query), `key_facts jsonb?`, `key_facts_updated_at?`, `is_self bool` (default false; partial unique index per `user_id` — at most one; excluded from People list/search/Dunbar/due-for-update), `deceased_date?` (presence = deceased), `organization?`, `job_title?`, `phones`/`emails`/`urls`/`social_profiles jsonb` (arrays of `{label, value}`), `addresses jsonb` (array of `{label, street, city, state, zip, country}`), `created_at`.
  - `middle_name`/`goes_by_other` fold into the same nicknames-style lookup for search and AI resolution across `converse`/`update-moment`/`update-group`/`person-facts`/`add-fact`.
  - Contact-info columns are their own isolated query in `ContactInfoSection.tsx`, never folded into the main person select (same pattern as `gender`) — a pre-migration 42703 hides one card instead of emptying the page.
- **relationships** — `id`, `user_id`, `person_a_id`, `person_b_id`, `kind` (`spouse`/`sibling`/`partner` — symmetric, stored once with `person_a_id < person_b_id` by uuid sort; `parent` — directional, `person_a_id` IS THE PARENT, no separate "child" kind), `ended_reason?` (spouse/partner only, only value `divorce` — death is read off the person's own `deceased_date`), `created_at`; unique(`person_a_id`, `person_b_id`, `kind`).
  - THE shared source of truth for family links. `_shared/relationships.ts` dual-writes here alongside reciprocal notes; `person-facts` cross-references it; `converse`/`update-moment`/`update-group` read it for "my mom/dad"; `Circle.tsx`/`FamilyTree.tsx` read AND write it directly.
  - Sibling/parent links auto-propagate across the WHOLE transitive sibling clique on every add (`syncFamilyClique`), seeded from both existing sibling rows and shared parentage. Spouse links auto-propagate to a co-parent role on the other's existing kids, guarded against remarriage.
- **person_pets** — `person_id` + `pet_id` (PK), index on `pet_id`. RLS is a subquery through `pets` (no denormalized `user_id`), so a mistake fails SILENTLY — verify with write-then-read-back. Deleting every linked person leaves an orphan `pets` row (accepted; orphans still list in People with no owner chips, so they stay reachable).
- **pets** — `id`, `user_id`, `name`, `species?` (FREE TEXT, deliberately no CHECK), `breed?`, `birth_date?`, `adopted_date?` ("gotcha day"), `deceased_date?` (presence = passed away), `notes?`, `attributes jsonb []` (`{label, value}` — Barn/Tank/Vet/microchip live here, not in columns), `created_at`. A real table, not a jsonb column on `people`: a household pet belongs to both spouses and must be edited once. NO unique index on `name`.
- **reminders** — `id`, `person_id`, `label` ("Birthday"/"Anniversary"), `month`, `day`, `year?` (nullable; a life date only becomes a milestone count-up once the year is known). No automatic sending exists. No DB unique constraint — `lib/reminders.ts` does an app-level upsert on `person_id` + label.

### Events

- **moments** — `id`, `user_id`, `raw_description` (user's words only — never assistant turns), `summary?` (AI cache), `occasion?`, `location?` (free text), `when_text?` (free text, kept verbatim), `event_date?` (best-guess real date — exact from a calendar DTSTART, AI-guessed otherwise; sorting/display only, **NOT ground truth**; null = fall back to `created_at`), `event_end_date?` (null = single-day/unknown), `details jsonb?` (open-ended by design, still dormant for writes), `weather jsonb?`, `weather_fetched_at?`, `game jsonb?`, `game_fetched_at?`, `game_candidates jsonb?`, `game_dismissed bool`, `dismissed_person_ids jsonb []`, `parent_moment_id uuid?`, `created_at`.
  - Enrichment caches have THREE states and the difference matters: null = never looked; `{"status":"not_found"}` = looked, found nothing (never re-fetch); `{"status":"ok",…}` = real data. A fourth, `{"status":"too_soon"}`, parks a future-dated event and is the ONE value `enrich-event` revisits, once the date has passed — same for a game stored while still `Scheduled` (its 0–0 is not a real score).
  - `parent_moment_id`: self-referencing FK, ON DELETE SET NULL, CHECK `parent_moment_id != id`. Sub-events — one level deep in the UI, arbitrary depth in schema, mirrors `groups.parent_group_id`. Renders as the ancestor chain "Trip / Day 2" in every list an event is PICKED from (`lib/momentDisplayName.ts`); pickers add the event date too. Read-only event lists stay bare. Parentage comes from `lib/moments.ts`'s `fetchMomentParentIds()` — its own fail-open query, never a column on a page's main select.
- **moment_links** — `id`, `user_id`, `moment_a_id`, `moment_b_id` (both FK `moments` ON DELETE CASCADE), `created_at`; unique(`moment_a_id`, `moment_b_id`), CHECK `moment_a_id < moment_b_id`, index on `moment_b_id`. "Related events": a SYMMETRIC link where neither event is part of the other — the case `parent_moment_id` can't express and merge would destroy. The CHECK is what makes the unique index a real duplicate guard, so every caller must go through `lib/relatedEvents.ts`'s `normalizeLinkPair`. Two FKs to `moments`, so embeds would need qualifying (PGRST201) — the lib does two round trips instead. RLS checks `user_id` AND that both moments belong to the caller.
- **moment_pets** — `moment_id` + `pet_id` (PK), index on `pet_id`. A pet's attendance is a row here, NOT a `notes` row the way a person's is. Consequence: a pet has no per-event note, so tagging one deliberately does NOT null `moments.summary`. RLS checks BOTH sides (pets AND moments) — `moment_id` is client-supplied. Subquery policy, so mistakes fail SILENTLY: verify with write-then-read-back.
- **moment_groups** — `moment_id` + `group_id` (PK).
- **moment_tags** — `moment_id` + `tag_id` (PK), index on `tag_id`.
- **notes** — `id`, `person_id?`, `moment_id?`, `group_id?` (CHECK: `person_id` OR `group_id` OR `moment_id`; the moment_id-only case has its own RLS policy), `source?` (`home` = written by converse, `calendar_import` = ImportReview's save-as-note), `source_group_id?` (fact captured via a group chat), `content`, `created_at`.
  - Attendance on an event IS the existence of a note with that `moment_id`; untagging nulls `moment_id`, never deletes.
  - ⚠ two FKs to `groups`: embeds must be qualified (`groups!notes_source_group_id_fkey`) or PostgREST errors (PGRST201).

### Groups and tags

- **groups** — `id`, `user_id`, `name`, `summary?` (AI cache), `group_type?` (plain text holding the type's NAME — no longer CHECK-constrained; the fixed five became a user-owned list, see `group_types`), `group_type_suggestion_dismissed bool` (not null, default false — dismissal for the "looks like a family group?" nudge, separate from the membership dismissals), `dismissed_person_ids jsonb []`, `dismissed_group_ids jsonb []`, `color_index smallint?` (index into `subgroupPalette` in `lib/theme.ts`, NOT a hex, so the palette stays the source of truth; NULL = auto-assigned by position; read in its own isolated query), `suggestions_enabled bool` (per-group opt-out for the member-suggestion signal; default false), `parent_group_id uuid?`, `created_at`.
  - `parent_group_id`: self-referencing FK, ON DELETE SET NULL, CHECK `parent_group_id != id`. Nested subgroups at ARBITRARY DEPTH in both schema and UI.
  - Subgroup membership WRITES are independent of the parent's: no sync trigger, and a new subgroup starts empty. Upward, a subgroup's members ARE the parent's members — DERIVED at render by `lib/groupRollup.ts` at any depth, never written to `person_groups`.
  - A person can sit in several sibling subgroups at once, which is why member chips carry a LIST of colour dots. There is NO colour column beyond the manual `color_index` — automatic subgroup colours are assigned client-side by position (`lib/subgroupColors.ts`) and persist nowhere.
  - Subgroup names render as the FULL ancestor chain "A / B / C" APP-WIDE, so same-named subgroups under different parents stay distinguishable. `lib/groupDisplayName.ts` owns the format (its 3rd arg `parentById` is what turns on full-chain walking) and also exports `isSelfOrDescendant()`, the cycle guard every reparenting path uses. `lib/groupRoster.ts`'s `useGroupRoster()` serves `label(id, fallbackName)` to any site holding only `{id, name}`. Two deliberate BARE exceptions: a group's own h1 on GroupDetail, and the subgroup tiles on the parent's own page.
- **person_groups** — `person_id` + `group_id` (PK). THE definition of membership (explicit only; event attendees are never members, only suggestions). A row is only ever written for the group it was added to — what the UI shows as a group's members is these rows PLUS the subgroup rollup, computed at render, never stored.
- **group_associations** — `id`, `group_id_a`, `group_id_b` (symmetric, normalized a<b by UUID string sort), `created_at`.
- **group_types** — `id`, `user_id`, `name`, `created_at`; unique index on (`user_id`, `lower(name)`). A user-owned, growing list like `tags`. `groups.group_type` stores the NAME, not a FK — a rename in Manage Group Types rewrites the matching groups in the same step.
- **tags** — `id`, `user_id`, `name`, `created_at`; unique index on (`user_id`, `lower(name)`) — case-insensitive dedup so "Milestone"/"milestone" can't fork into two filter entries. A real table rather than a `text[]`, so a tag has a canonical identity for cross-event reuse.

### Notebooks (the internal side — §1)

- **notebooks** — `id`, `user_id`, `name`, `ai_visible bool` (default true), `locked bool` (default false), `created_at`. `ai_visible` gates the Home chat ONLY — `converse` filters on it in the query, not at render; global search always reads every notebook. `locked` is enforced INDEPENDENTLY: `converse` and `searchCorpus` each filter on `locked = false` in their own right, so a locked notebook stays out of chat even with `ai_visible` true.
- **notebook_entries** — `id`, `user_id`, `notebook_id` (FK cascade), `content` (editor HTML), `content_text` (the same thing flattened to words — STORED, not derived: search would match "strong" inside every bold word, and `converse` runs on Deno with no DOM. Written together with `content` in `lib/notebooks.ts` so they can't drift. Null on pre-editor rows, where `content` IS plain text), `entry_date?` (date — nullable, display/sort only, same as `moments.event_date`; its presence is the ONLY difference between a running list and a dated log — there is no layout column and no mode to pick), `created_at`.
- **notebook_entry_people** — (`entry_id`, `person_id`) composite PK, both FKs cascade. Two-sided subquery RLS: `with check` validates BOTH sides. ⚠ this class of policy fails SILENTLY when wrong — verify by write-then-hard-reload, not by watching the UI.
- **notebook_pins** — `user_id` PK, `pin_hash`, `created_at`. One PIN per ACCOUNT, not per notebook. Hashed with pgcrypto `crypt()`/`gen_salt('bf')` server-side; the PIN is never stored or compared in the browser. Three `SECURITY DEFINER` RPCs: `notebook_pin_status()`, `set_notebook_pin(new, current)` (requires the current PIN once one is set), `verify_notebook_pin(pin)`. Reset path is Supabase's own password re-auth, so a forgotten PIN never strands a notebook.

## 9. Product & UX decisions (the standing "why")

- **iPhone app is the real end goal** — weigh iPhone Safari support in every web-API choice (this decided a server transcriber over Web Speech). Note the reason, corrected 2026-08-18: Web Speech is *supported* in iOS Safari (14.5+), it is merely unreliable there, so it serves as an optional visual aid on other browsers rather than being unusable everywhere.
- Email over push (scope); one shared People concept under everything. (The "web/PWA now, not native" half of this is superseded — see the Capacitor entry below.)
- **Talk, don't fill out forms (mostly):** most corrections/dates/nicknames are set conversationally via AI classification (the fact bar), not form fields. Exceptions, kept consistent across Person/Event/Group: rename pencils (name/title fields) and manual group/attendee tagging (search-and-add pickers), plus note edit/delete, merge/delete — these are direct-manipulation controls, not AI-classified.
- **Flexible data over rigid structure** (jsonb `details`, free-text `when_text`): great for AI-driven recall, deliberately bad for structured reporting — don't "clean up" without asking. `event_date` was an explicit founder-approved exception (AI resolves "last week" to a real date for sorting only).
- **Never silently assert an inference.** Relationship links, new people from mentions, shared parents, last names — all "suggest, don't assert" banners unless the match is exact-full-name confident. Key Facts never infer or pad. Exception (founder decision 2026-07-20): siblings named together in the same statement link directly to each other, no suggestion banner — same certainty as the stated pair, not a separate guess.
- **Placeholder people get renamed, not duplicated** ("Clare's mom" → real name = rename). One placeholder per distinct individual.
- Broad questions synthesize everything; never dead-end a miss.
- Membership ≠ attendance: `person_groups` is the only membership truth; attendees of a group's events are suggestions.
- Merges: the record you search for survives; the one you're standing on folds away.
- **Never make the user feel bad about forgetting** — the app is a private pre-event briefing tool, not live assistance. Two query modes: specific lookup (built) and "memory lane" curated overview (NOT built — item toward §8).
- **Input philosophy:** incremental over exhaustive; a fragment is a valid entry; AI carries the cognitive load (confirmation over free recall); "good enough" is the default. Proactive nudges: AI-selected type (action/reflection/memory-mining), trigger mechanism not designed yet.
- Security honesty tiers (item 23): encryption at rest/in transit = claimable now; E2E = roadmap only (conflicts with AI reading content today). Reasoning written up for the founder in `SECURITY.md` §4 — three options (app-layer column encryption / on-device AI in a native app / full E2EE), none committed to; app-layer is the recommended first step, but only after closed signups + 2FA + verified isolation + tested backups.
- **Touch fixes 2026-08-01 (found opening the PWA on a real iPhone):** `src/lib/touch.ts`'s `IS_TOUCH` (`matchMedia('(hover: none)')`, computed once at module load — a touchscreen laptop CAN hover and keeps the hover-only behavior). **13 hover-gated controls across `GroupDetail`/`EventDetail`/`PersonDetail`/`FamilyTree`/`ImportReview` were completely unreachable on touch** (member/attendee/tag/group remove ×, family-tree relationship remove, note edit/delete) — all now render on `hovered || IS_TOUCH`. `index.css` gained a `@media (hover: none)` block: inputs floored at 16px (iOS force-zooms anything smaller on focus and never zooms back — 7 inputs were 0.85–0.95rem), and `.touch-action` gives the now-always-visible 18px/10px-icon buttons a 32px minimum target. Note delete now `confirm()`s on both platforms — it's permanent, and the reveal fix put it one stray thumb-tap away. **Deliberately NOT fixed: general sizing** (body text mostly 0.85–0.9rem, mouse-era layout) — that's the redesign, and patching it piecemeal means doing it twice.
- **PWA shipped 2026-08-01 → `PWA.md`** (install steps, name-change checklist, decisions). `public/manifest.webmanifest` (standalone, theme `#2E4034`, bg `#F7F5F2`), iOS meta tags + `apple-touch-icon` in `index.html`, four PNG icons in `public/` generated by `scripts/generate-icons.py` (regenerable — edit `LETTER`/`BG`/`FG` and re-run; note there is no Python on the founder’s machine, so `PWA.md` documents a browser-canvas fallback that is what has actually been used). **No service worker, deliberately:** the app is useless offline anyway (every screen hits the DB/AI), so its only real effect would be serving a stale build after a deploy to the one user who can't debug it. **`index.html`'s viewport deliberately omits `viewport-fit=cover`** — without it iOS auto-insets the web view away from the home indicator, keeping Home's fixed-bottom chat bar clear with zero CSS changes; adding it would require safe-area padding on every fixed element.
- **Native iPhone: Capacitor + a cloud Mac (founder decision 2026-08-22).** **Supersedes the 2026-08-01 "PWA first, NOT Capacitor" call**, which was made because the founder works on a PC with only borrowed Mac access — renting a Mac in the cloud for builds and submissions removes that constraint. Driver: founder wants real App Store distribution, because "saving to your home screen from Chrome is not user friendly" and "everyone uses their phone every day, so the app needs to be mobile first." - **Mobile shape: a calmer version, not a shrunken desktop app** (founder, 2026-08-22). Same data, phone-shaped, one thing at a time, glanceable. Pairs with the §9 note above about not patching sizing piecemeal — that redesign is this.

- **Cost model: measure first, then a capped free tier** (founder, 2026-08-22). Find real per-user cost before opening signups, then a free tier with a hard cap so nobody's usage costs money unexpectedly. ## 12. Regression guards (hard-won one-liners — full stories in PROJECT_HISTORY.md §9)

- **A former name is a SURNAME alias, not another nickname** (item 101, 2026-08-21). Every other alias field (`nicknames`, `middle_name`, `goes_by_other`) folds into `personNameKeys().givens`, by explicit design — "a nickname can't quietly overrule a surname that disagrees". Filing a maiden name there records "Jenkins" as a FIRST name, and Sarah Jenkins still fails to match Sarah Mitchell. It belongs in `surnames`, via the dedicated 4th argument. Also: former-name keys are claimed in a SECOND pass that skips any key a current name already owns (`claimFormerNameKeys`) — otherwise a real Sarah Jenkins on file loses her own lookup the moment an unrelated Sarah records "Jenkins" as a former name, because the shared ambiguity guard deletes the collided key and then NEITHER resolves.
- **A geocoder answers a vague query confidently, not with an error** (item 21, 2026-08-17). `moments.location` is free text, and Open-Meteo takes a single place NAME, not an address — "Coors Field, Denver, Colorado" returns nothing at all, so a multi-part string has to be tried a piece at a time. Taking the LAST piece is the obvious move and is the trap: the tail of a US address is the state, and searching "Colorado" returns **Colorado City, TEXAS** — 700 miles off, no error, and a perfectly plausible-looking temperature. Try segments LEFT to right (specific first), and when the caller knows the region, verify `admin1` matches instead of trusting the first hit — "Oracle Park" resolves to Oracle, ARIZONA, not the San Francisco ballpark. Several major venues (MetLife Stadium, Empower Field) aren't in the gazetteer at all, which is why the code geocodes a CITY and never a venue name.
- **An empty result and a failed call must never look the same** (2026-08-19, from §10's API-key outage). `scan-calendar-sources`'s `callExtraction` returned `[]` both for "the AI read these events and suggested nothing" and for "the API answered 401" — which is how nine days of dead syncs reported "All synced — nothing new found." Every AI function here fails open by design (cached facts, hardcoded prompts, an empty candidate list); that is the right behaviour and it is exactly what hides an outage, so the failure has to travel alongside the result: `{ items, failed }` out of the helper, an `extractionFailures` count out of the function, and wording in the UI that says the calendar couldn't be read. Apply the same test anywhere a fallback is indistinguishable from a legitimate empty answer.
- **The same field from the same API can change format between endpoints** (item 21, 2026-08-17). ESPN reports a venue's state as a full name for MLB ("Pennsylvania", "Ontario") and as a two-letter code for the NFL, NBA, NHL and college feeds ("GA", "CO", "MB"). A raw string comparison against Open-Meteo's full-name `admin1` would have matched baseball and **silently rejected the weather box for every other league** — the failure mode is a missing box, not an error. `normalizeRegion()` maps both forms to one, and returns null for anything unrecognised (some international venues report a country) so the guard degrades to "don't guard" rather than "reject everything".
- **Caching only works if failure gets cached too** (item 21, 2026-08-17). The weather archive answers any future date with a hard 400. Because a thrown failure deliberately writes nothing (so transient outages retry), a future-dated event would have re-hit the provider on **every single page view, forever**. Anything with a date needs a third state beyond "got it"/"nothing there": `too_soon`, stored so it stops asking, and revisited exactly once after the date passes. Same shape for a game found while still `Scheduled` — its stored 0–0 is not a real score, and would have been frozen as one.
- **An inline `style` silently beats a media query** (Notebooks nav fix, 2026-08-18). This app styles everything with inline `style={{}}` objects, so any value a breakpoint needs to override CANNOT live there — the CSS rule loses, with no warning and no devtools strikethrough to notice in passing. `navStyles.linkLabel` set `fontSize` inline, so the phone-only step-down in `index.css` did nothing and the tab label clipped. The font-size now lives only in CSS. `.nav-wordmark` had already learned this — its comment says navStyles.wordmark sets no `display` "so this rule wins uncontested" — which is the general rule, not a note about that one class.
- **A flex row with `flex-basis: 0` starves its longest child** (same fix). Six nav tabs from a 0 basis each got an identical 40px, so "Notebooks" overflowed its box and printed 3.3px on top of "Groups" — with `overflow: visible` there is no clipping to make it obvious, just two words touching. Use `flex: 1 1 auto` when the children's own widths differ and matter. Also: measure this by comparing the LABELS' bounding rects, not the buttons' — the buttons never overlapped.
- **`platform_stats()` is the ONLY intentional RLS bypass** (`SECURITY DEFINER`, granted to `anon` for the Landing page's databox). It is safe solely because it returns four counts. Never extend it to return rows, names, or anything per-record — that turns it into a public data leak. Query 4 of `migrations_manual/2026-08-01-rls-audit.sql` exists to confirm it's still the only such function.
- **Silent RLS failure is the house bug:** any Supabase write that only checks `if (data)` fails silently — always check `.error`, and gate every function on a valid `user` up front (401 "log out and back in" on stale sessions). The AI will cheerfully claim it saved when nothing did.
- **In a multi-step write, the destructive step goes last and every step before it must be checked** (items 91/93, 2026-08-11). Merges move rows off a duplicate and then delete it — and that delete cascades, so an unchecked move that failed halfway meant the delete destroyed the rows that never moved. There is no transaction from the browser client, so the rule is: stop at the first failure and never reach the destructive step. A half-finished merge is recoverable by merging again; a cascade is not. Corollary for the message — if only the final delete fails, say the data moved but the shell remains, don't imply loss.
- **Paging without an `.order()` is worse than the truncation it fixes** — Postgres may return rows in a different order per page, so a row lands in two pages or in neither. `fetchAllRows` (both twins) exists so this can't be got wrong; never hand-roll the loop. When the sort key isn't unique (a name), add a secondary `.order('id')`, or rows shuffle between pages for the same reason.
- **A roster loaded once per visit goes stale the moment the page itself creates a row** (2026-08-18, founder report). All four import review queues load `people` once and hand the array down to every card, so a profile created by accepting one card was invisible to the next card's "link to someone existing" until a full page reload — which is exactly the case a 1000-contact import hits, where the same person is listed two or three times. Creating the row is not the end of the job: push it back into the parent's in-memory list, and pull it out again if an undo deletes it, or a dead profile stays searchable. `handleTagCreated`/`handleGroupCreated`/`handleMomentCreated` already did this for their own lists — people were simply the one that got missed.
- **Every AI feature degrades quietly, so an invalid API key looks like an empty app, not an outage** (2026-08-12, §10). `ANTHROPIC_API_KEY` was rejected with `401 authentication_error` across all 10 functions that read it, and nothing anywhere said so: `person-facts` returns `extraction_failed` and serves stale cache, `suggest-prompts` returns hardcoded fallbacks. Those fallbacks are correct behaviour for a blip and the wrong behaviour for a dead key. It surfaced only because four real profiles had `key_facts` NULL. When an AI feature "just isn't doing anything," check the key before the prompt — and note the CLI has no `functions logs`, so pinning down when it broke needs the Dashboard.
- **Two tap targets ~6px apart is a mis-tap, whatever the design says** (item 14, 2026-08-12, founder report). The nav bar's `gap` is `space.xl` and not a small value on purpose: at `space.sm` the last control sat beside the account avatar and reaching for one opened the other. Meeting the 44px touch minimum per control is not sufficient — the DEAD SPACE between two controls that do very different things is its own requirement.
- **Never mix a CSS shorthand with its longhand across a base style and the style layered over it** (item 14, 2026-08-12 — second occurrence, SearchAddPicker hit it with `border` first). `background: 'none'` in the base plus `backgroundColor` in the active variant makes React warn on EVERY rerender and drop one of them. Pick one form and use it in both halves. Inline-style-only app, so this pattern recurs wherever there's a highlighted row.
- **Focus an input the moment it exists, with a `useCallback` ref — not an effect** (item 14, 2026-08-12). `useEffect` + `requestAnimationFrame(() => ref.current.focus())` looked right and silently lost the focus in a real browser; a callback ref fires when the element attaches and can't race. It must be `useCallback`'d — an inline arrow is a new identity every render, so React detaches/reattaches and yanks the caret to the start on every keystroke.
- **A test that needs `.env` passes locally and fails for everyone else** (2026-08-12). `src/lib/supabase.ts` calls `createClient()` at module scope, so importing ANY `src/lib` module builds a real client — 12 test suites died on `supabaseUrl is required` in GitHub Actions (no `.env` there, by design) while passing on every dev machine. `vite.config.ts`'s `test.env` block now supplies placeholders. The general trap: a gitignored file that only exists on your machine is invisible to the check that's supposed to catch you. Anything added at module scope in `src/lib` inherits this — prefer lazy/injected clients over top-level construction.
- **A lint/type config that isn't being read reports "clean" forever** (item 95, 2026-08-11): the oxlint config sat at `_oxlintrc.json` for weeks while oxlint looked for `.oxlintrc.json`, so the one rule set to `error` was never enforced. If a checker has never failed, confirm it's actually loading its config before trusting it. Same class: `tsconfig.app.json` only includes `src/`, so the Edge Functions were typechecked by nothing at all until `npm run check:functions`.
- **NEVER pass `--no-verify-jwt` to `supabase functions deploy`, and know that a plain redeploy does NOT undo it** (2026-08-11, self-inflicted). The flag turns off the PLATFORM's auth gate, and the setting persists server-side per function — redeploying without the flag leaves it off. Only `PATCH /v1/projects/{ref}/functions/{slug}` with `{"verify_jwt": true}` puts it back. **The tell is the token-free check itself:** a correctly gated function answers `UNAUTHORIZED_NO_AUTH_HEADER`; if it answers with the function's OWN 401 instead, the platform gate is off and every request is reaching your code. Audit the whole project in one read with `GET /v1/projects/{ref}/functions` and look at `verify_jwt`.
- **A twin module that only one side updates is a silent wrong answer, not an error** (item 94, 2026-08-11). `groupNames.ts`/`groupDisplayName.ts` drifted for three months after only the app copy learned to qualify names through the full ancestor chain. Every `src/lib` ↔ `supabase/functions/_shared` pair needs a parity test asserting both produce the same output — `groupRollupParity`, `groupNamesParity`, `familyRoster`, `kinship`, `nameMatch` are the model. Adding a twin without one is how this comes back.
- **Bare first names/nicknames only resolve when unique account-wide** ("two Bobs"); relationship auto-linking additionally requires name-as-typed == full name on file. Any new AI shorthand (group names too) must handle non-unique.
- **Model JSON is never clean:** slice first `{` to last `}`, retry once on parse failure, regex-extract `"reply"` as last resort. Assistant-prefill (`{role:"assistant","{"}`) is NOT supported — hard API error. Give `max_tokens` headroom for the richest turn (converse: 4096) — truncation = silent JSON failure. Remove unused fields from prompt schemas (dead output budget truncated Key Facts).
- **Save per turn, never gate on "done"** — users don't reply to closing questions.
- **A name merely MENTIONED in a story is never auto-created as a profile** (2026-08-02) — it's written as a general note on the event (`person_id: null`) and offered as a one-tap banner. The note must be written server-side at capture time, never deferred to the banner: an unanswered banner has to leave the detail intact, because the note is the only record of that person. Applies to `converse` and `update-moment`; any new capture surface needs the same split.
- Build `raw_description` from `role === "user"` messages only (assistant turns can contain retry garbage).
- **Any function resolving user shorthand needs the FULL rosters** (people AND other events) — narrower context than the user's mental model = wrong guesses ("Triple Bypass" = a bike race, not surgery).
- Chips always render canonical `nameById[id]`, never the model's raw spelling; `.trim()` before name matching.
- Prompts must explicitly require a notes row for every "X was there" mention — attendance IS the note link.
- **PostgREST:** 2 FKs to one table ⇒ qualify embeds (`table!constraint`) or every consumer errors; `.eq()` on an embedded resource filters the embed's own rows — use two queries when you need the full related set. Nested-join TS types lie about cardinality — trust the schema, cast `as unknown as T`.
- `verbatimModuleSyntax`: type-only imports (`import { type X }`). Run `npm run build` locally — clean dev ≠ clean build.
- Vercel env changes need a fresh redeploy (build-time baking). Pushes absent (not failed) from Vercel's deploy list ⇒ check vercel-status.com; CLI is the fallback.
- Prompt-cache guards: stable-first/volatile-last, no timestamps/UUIDs in system prompts, deterministic JSON serialization, explicit `.order()` everywhere (§5).
- A Key Facts name with no chip = the name didn't uniquely resolve (dupe person or ambiguous name in the source note) — that's the signal, not a rendering bug.
- Before loosening any name-matching/confidence check, grep PROJECT_HISTORY for why it was added first — `person-facts`'s exact-full-name-match rule looks overly strict in isolation but exists specifically to stop a real false-positive (Gus/Olivia, 2026-07-19); "unambiguous in the roster" ≠ "confirmed identity," since the named person may not be in the system at all.
- Fix classes of bugs, not instances: `converse`'s siblings (`update-moment`/`update-group`) have repeatedly harbored the same bug (JSON fences, max_tokens, silent errors, missing rosters) — when one function gets a reliability fix, check them all. Same for the two independent name-resolution paths (`relationships.ts` and `person-facts`).
- **A confident match and a confirmed suggestion must write the exact same both-sides notes** — `relationships.ts`'s direct-write path did, but `RelationshipSuggestions.tsx`'s confirm handlers only ever wrote onto the newly linked/created person, never back onto the subject, until fixed 2026-07-20 (found via the Sucre-brothers inconsistent-siblings report: whichever profile the fact was typed on could end up with nothing). Any new relationship-suggestion type needs the same both-sides write, not just the "obvious" direction.
- **A "does this note already exist" dedupe check must match the EXACT deterministic text, never a loose "mentions this name + a family-shaped keyword" heuristic** — the loose version (`relationships.ts`, fixed 2026-07-20) false-positived on the SUBJECT's own original sentence (e.g. "Her siblings are Clare, Bridget, and Patrick" already contains "Clare" + the word "siblings"), silently blocking the subject from ever getting their OWN reciprocal note while everyone else correctly got theirs pointing back at them — found via the Berzins-family report, where Caroline (the one person who'd actually typed the fact) was the one left incomplete, not her siblings.
- **A `.select()` embedding a table that doesn't exist yet fails the WHOLE query, not just that one field** — adding `moment_tags(tags(...))` to Events.tsx/EventDetail.tsx's existing moments query, before the item-28 migration had been run, turned "no tags yet" into "Events page shows zero events" (PostgREST returns `data: null` for the entire row set, and the existing `?? []` fallback silently swallows that into an empty list, same silent-failure shape as the RLS guard above). Caught before push by testing directly against the live schema (`supabase.from(...).select(...)` via the browser console) rather than trusting `npm run build`, which can't see this. Any new embed on an existing, page-critical query needs the migration confirmed live FIRST — don't push code that adds a new embed until the table it joins actually exists in production.
- **Server-side "today" must never be `new Date()` on its own** — Edge Functions run in UTC, so an evening event in any US time zone (UTC has already rolled to the next calendar day) got resolved/dated tomorrow instead of today. Fixed 2026-07-24: `converse`/`update-moment`'s "today" and `scan-calendar-sources`' UTC-stamped DTSTART parsing now go through `_shared/tz.ts`, formatted in the user's own `user_settings.time_zone` (defaults to `'UTC'` — the old behavior — until set). Any future code computing "today"/"now" server-side for date resolution needs the same treatment, not a bare `new Date()`.
- **A bare `YYYY-MM-DD` string handed to `new Date(...)` parses as UTC midnight, not local midnight** — same underlying gotcha as the guard above, but client-side: `EventDetail.tsx` displayed `event_date` via `new Date(moment.event_date).toLocaleDateString(...)`, which in a negative-UTC zone rolls the displayed date back a day. `dates.ts`'s `eventSortDate`/`formatFullDate` already parse this correctly (append `T00:00:00`, tested in `dates.test.ts`) — `EventDetail.tsx` just wasn't using them for this one line, fixed 2026-07-24. Any new code displaying a bare date column must go through `dates.ts`, never construct `new Date()` from it directly.
- **Display text derived from a navigation-time prop (breadcrumb label) goes stale the moment the underlying record is renamed mid-visit** — `PersonDetail.tsx` had every nudge/fact-bar/banner string keyed off the `personName` prop instead of the freshly-loaded `person` state, invisible until the manual "add person" flow (2026-07-20) made same-visit renames the common case instead of the rare one. Any page with an in-place rename control needs its own display text to track live state, not what it was called when you navigated in.
- **A blank-shell record's cached AI summary can be generated against its placeholder name/content before it's ever filled in** — `GroupDetail.tsx`'s rename didn't invalidate the cached summary (only membership changes did), so a manually-created group (2026-07-20) could get summarized as "New group" and stay that way forever. Any manual-create-then-fill-in flow needs its rename/edit paths to invalidate the same caches the AI-driven paths already do.
